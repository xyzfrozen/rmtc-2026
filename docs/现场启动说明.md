# 现场启动说明

程序在你自己的 Ubuntu 电脑运行，网线连接裁判网络。裁判发送本队感知，本机程序计算动作并发回；第二阶段另用 HTTP 调用裁判的统一 AI 网关。ROS 话题通信与 HTTP 网关是两条链路，网关健康检查通过不代表已经收到感知。

本机准备由 `build.sh` 完成。新电脑按[迁移与验收](迁移与验收.md)执行，本文不代表已经在那台机器验收。

2026-10-30已按《参赛手册》更新：提前领取分配的静态IPv4；模型输出上限为512 token；双裁判赛场换场时重新核对域、席位、网关和令牌。手册里的IP和域编号仍是示例。

## 1. 提前构建一次

在克隆后的仓库目录打开终端；以下使用迁移默认目录，若实际位置不同则替换为自己的仓库路径：

```bash
cd "$HOME/Documents/rmtc-2026"
bash build.sh
```

需要已有 ROS 2 Humble、CMake、C++17 编译器、JsonCpp 和 libcurl 开发库。新电脑先按迁移文档补齐；编译输出末尾应显示测试通过。正式比赛不需要启动本地裁判、DSH 或 OpenCode。

本项目由CMake直接构建，`start.sh`自动加载系统ROS并启动本目录的可执行文件，无需寻找其他工作空间中的同名程序或不存在的`install/setup.bash`。依赖下载和构建应在到场前完成。

## 2. 领取静态地址，再设置有线连接

手册第3页要求赛前一天在群内查看分配的IPv4地址和子网掩码。还须确认本场 `ROS_DOMAIN_ID`、A/B/C/D席位、裁判机IP、AI完整请求地址和本场席位令牌。上述实际值尚未提供，不能照抄手册中的`192.168.50.11`、`27`或网关示例。

在Ubuntu“设置 → 网络 → 对应有线连接的齿轮 → IPv4”选择“手动”，填写分配的地址和掩码；按手册步骤，网关和DNS留空。应用后重新连接并检查地址；若工作人员另发接入单，遵照实际分配。本文和启动脚本不会自动修改网络或防火墙。

查看有线网卡名和当前地址：

```bash
ip -4 -brief address
```

有线网卡通常形如 `enp…`，以实际输出为准。建议正式联调时断开无关 Wi-Fi/VPN；启动器也会把 DDS 绑定到配置的有线 IPv4 地址。ROS 需要在该网络允许发现和双向 UDP 通信。

同一网络规划下，换A/B/C/D席位不需要重改设备IP；设备IP、长期队伍ID和本场席位是三种不同信息。没有网口时提前验证USB有线网卡。若使用虚拟机，在实际运行ROS的Ubuntu来宾系统检查地址，通常桥接到物理有线网卡；宿主机与来宾不能共用同一静态IP。能SSH登录或ping通都不等于ROS双向链路已通。

诊断路由时，`ip route get`和`ping -c 3`后面填写裁判机的完整实际IP；手册中的`192.168.50.*`是占位写法，不能原样作为地址执行。

## 3. 配置网卡和网关，每场参数写在启动命令中

首次执行：

```bash
test -f config/match.json || cp config/match.example.json config/match.json
```

用编辑器打开 `config/match.json`，填写：

```json
{
  "gateway_url":"http://192.168.1.100:8080/v1/chat/completions",
  "network_interface":"enp3s0"
}
```

**这里的IP、端口和网卡名只是格式示例，必须替换成现场实际值。** 两项都是字符串，最后一项后面不加逗号。

每次启动和`--check`都必须在命令里填写下面三项；脚本不再从JSON或终端已有环境变量中继承它们，漏填就报错。旧版JSON中遗留的同名字段也不再生效。

| 命令参数 | 填什么 | 换场时怎么处理 |
|---|---|---|
| `--ros-domain-id` | 裁判分配的整数域编号；脚本用它设置`ROS_DOMAIN_ID` | 每场核对，换裁判场地可能改变 |
| `--team` | 本场席位`A`、`B`、`C`或`D`，不是长期队伍ID | 第一阶段必须是`A`；第二阶段按本场分配填写 |
| `--team-name` | 报名队名，用引号包住 | 通常保持相同；换席位无需改名 |

队名最多96个UTF-8字节，不能含换行。需要更换网关时，可以更新JSON，或在检查和启动两条命令中都追加`--gateway-url 'http://实际裁判IP:实际端口/v1/chat/completions'`；命令中的地址优先。

`gateway_url` 必须以 `/v1/chat/completions` 结尾。正式比赛不是 `127.0.0.1`，也不是你的 DeepSeek 开发API地址。程序会自动发送 `model:"deepseek-flash"`、`max_tokens:512`、`thinking:{"type":"disabled"}`、JSON输出模式、固定长度请求体和非流式请求，不需要你手填这些字段。512是输出token上限，不是请求体长度。

## 4. 开赛前检查

```bash
bash start.sh stage1 --ros-domain-id 27 --team A --team-name '你的实际队名' --check
bash start.sh stage2 --ros-domain-id 29 --team B --team-name '你的实际队名' --check
```

**27、29和第二阶段的B只是示例，替换为本场实际域与席位；检查和随后启动必须用相同参数。** 第一条仅在参加第一阶段时使用，第二条用于正式网关的第二阶段检查并访问公开 `/healthz`，不输入令牌、不发送模型请求、不消耗调用配额。检查失败会说明哪项配置缺失。脚本自动设置 `ROS_LOCALHOST_ONLY=0`、命令指定的 `ROS_DOMAIN_ID` 和 Fast DDS；正式有线比赛不要加 `--local`，这个选项只用于同机练习。

公开练习包v1.1没有`/healthz`，本机练习按[本机练习与截图](本机练习与截图.md)直接启动，不用此健康检查。

如另开诊断终端，应加载同一ROS环境、域和DDS网卡配置；在程序启动后的日志目录可找到生成的`dds.xml`，在该终端把`FASTRTPS_DEFAULT_PROFILES_FILE`设为它的绝对路径。实际检录须完整看到“本队感知 → 本队程序动作 → 后续`self.last_action`回执”，只看到话题名或感知不够。不要向其他队伍席位发送测试动作。

## 5. 第一阶段启动

按裁判允许的启动时点运行：

```bash
bash start.sh stage1 --ros-domain-id 27 --team A --team-name '你的实际队名'
```

把27替换成第一阶段裁判给的域，队名改成你的报名队名。第一阶段不需要令牌，不调用AI，动作Tick为0–99，共10秒。应在裁判开赛前启动完毕，不能开赛后再找命令或编译。程序会等待裁判感知；等候时没有连续Tick输出不一定是故障。比赛结束由裁判确认结果，需要停程序时按 `Ctrl+C`。

## 6. 第二阶段启动和填写令牌

先确保旧程序已退出，把29、B和队名替换成本场实际值，然后运行：

```bash
bash start.sh stage2 --ros-domain-id 29 --team B --team-name '你的实际队名'
```

启动器会打印本阶段、席位、队名和`ROS_DOMAIN_ID`，核对无误后再输入令牌。若本场网关也变化，完整写法如下；检查时在同一条命令末尾加`--check`：

```bash
bash start.sh stage2 --ros-domain-id 29 --team B --team-name '你的实际队名' \
  --gateway-url 'http://实际裁判IP:实际端口/v1/chat/completions'
```

终端出现“粘贴本场席位令牌后按回车”时，粘贴裁判发放的令牌并按回车。**不会显示字符或星号，这是正常的。** 令牌只进入当前进程环境，不写配置、源码、命令参数或日志，也不会进入终端命令历史。不要粘贴此前用于开发的DeepSeek/API中转密钥。

输入后应看到 `Ready`；收到感知后显示Tick、血量、资源和动作。网关结果验证成功时会显示 `AI interpretation accepted`。日志中的 `http_success` 与 `accepted` 分别表示收到HTTP成功响应和事件JSON通过校验；正式任务计分资格仍由裁判本场、本席位的成功调用记录确认，前一场或联调中的调用不能替代。

第二阶段每Tick500ms、500Tick。本地动作不会等待网络；模型错误或超时仍继续运行。程序每场最多尝试80次，单个后台请求并发为1；网关返回额度耗尽或令牌无效时停止该场继续请求。若主办方变更限制，需在封存前按新要求重新核验配置。

## 7. 换场和异常处理

- 换场前按裁判要求停止旧程序，确认所属裁判赛场及其域、席位、网关和新令牌。在新启动命令中填写本场`--ros-domain-id`、`--team`和报名`--team-name`，网关变化则同步更新JSON或`--gateway-url`。双裁判赛场可各自使用A/B/C/D，席位相同不代表仍是同一场。令牌不会自动跨进程更新；重新部署后须按裁判要求领取新令牌。
- 只有 `Ready`、一直没有Tick：核对裁判是否已开赛、网卡IP、ROS域编号、席位和网线。能ping通不等于DDS话题已经通。
- Tick正常但AI失败：先看错误码。401通常是令牌不匹配；429且`quota_exceeded`是额度耗尽；502/504是网关或上游问题。程序会继续本地控制，不要因此重复开第二个程序。
- 提示已有程序运行：回到旧终端按 `Ctrl+C`。不要直接删除锁文件绕过检查。
- 需要重启时先服从裁判安排；进程停止期间会有动作空档。重启后程序从当前绝对坐标继续，但已探索地图和早先公告记忆不保留。

每次日志都在启动时打印的 `logs/日期时间-阶段-席位/` 中。`decisions.jsonl` 是本队决策和AI诊断；不要把令牌粘贴到复盘文档。现场排查只查看自己席位的话题；不要启动练习裁判或访问内部管理接口。

本队选择赛间不调整策略、代码和Prompt，换场只按裁判通知更新接入信息。当前程序没有登记人工`decision_type`切换，不需要额外的策略切换文件。

## 8. 接入依据

有线网络、ROS域、话题权限和令牌规则来自赛事通信协议v1.1、终版规则v1.2及10月30日收到的《参赛手册》（第3–7页）。静态IP流程和`max_tokens=512`采用手册要求；模型与透传字段采用你10月29日补充的主办方说明。关闭思考和JSON参数已核对 [DeepSeek思考模式说明](https://api-docs.deepseek.com/guides/thinking_mode/) 与 [JSON输出说明](https://api-docs.deepseek.com/guides/json_mode/)，接口选择依据 [Fast DDS网卡白名单说明](https://fast-dds.docs.eprosima.com/en/v2.6.11/fastdds/transport/whitelist.html)。程序能配置与本机测试通过，不代表尚未提供的裁判网络已经联调通过。
